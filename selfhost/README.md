# scc: the SafeC compiler, in SafeC

scc is a SafeC compiler written in SafeC. It compiles a SafeC program
straight to a WebAssembly binary: no LLVM and no linker. The C++ `safec`
can build it as a native tool or as WebAssembly, and scc can compile
itself. The WebAssembly build is the docs site's playground compiler; see
`web/README.md` for its API.

- `SUBSET.md` lists the part of the language scc compiles, and where it
  differs from `safec`.
- `web/README.md` is the playground API contract (`scc.js`).

## Building

The builds need the C++ `safec` (`compiler/`, on `PATH` or in `SAFEC`) and,
for the browser build, `clang` and `wasm-ld` from LLVM 21 or later.

```sh
./build.sh                  # native: build/scc
./build-web.sh              # browser: web/scc.wasm (deploy web/)
```

The native tool:

```
scc [-I dir] [-D NAME[=VALUE]] [-o out.wasm] [--check] input.sc
```

`--check` stops after semantic analysis. To run the module it writes:
`node web/run-node.mjs out.wasm [args]`. `node web/scc-cli.mjs file.sc
--run` compiles with `scc.wasm` through `scc.js`, which is the playground's
path, and runs the result.

## Testing

```sh
SAFEC_HOME=$PWD/.. python3 tests/difftest.py            # native scc
SAFEC_HOME=$PWD/.. python3 tests/difftest.py --scc-wasm web/scc.wasm
./ci.sh                     # everything CI runs
```

`tests/difftest.py` is a differential test. Each program in
`tests/docs/`, `tests/corpus/` and `tests/neg/` is compiled by both
compilers: by `safec` to a native binary that is then run, and by scc to
WebAssembly that is run under Node. The test passes when both accept or
both reject the program, and, when they accept it, the two runs give the
same stdout and exit code. `tests/docs/` holds the complete programs from
the SafeC book and reference (`tests/extract_docs.py` regenerates it from
a safec-docs checkout). The script also runs `compiler/tests/` (safec's own
regression tests) compile-only: the two compilers must agree on accept or
reject, and the result counts how many `EXPECT-ERROR` tests get every
expected diagnostic from scc too.

In a test, `// expect-error: text` requires that text in scc's diagnostics,
and `// stdin: text` feeds the program's standard input.

## Bootstrap

```sh
./bootstrap.sh [--test]
```

The script builds three stages:

| stage    | what it is                           | built by                           |
|----------|--------------------------------------|------------------------------------|
| stage 1  | `build/scc`, native                  | the C++ `safec`                    |
| stage 2  | `build/scc2.wasm`                    | stage 1, from scc's own source     |
| stage 3  | `build/scc3.wasm`                    | stage 2, running under Node        |

The bootstrap succeeds when stage 2 and stage 3 are byte-identical, which
means scc reproduces itself. With `--test`, the self-compiled stage 2 also
runs the whole differential test suite.

scc's source is flattened into one file for this (`tools/flatten.py`
inlines the `#include "..."` files that `src/scc_unity.sc` lists). Stage 2
uses the default capacities, because the flattened source (about 15,000
lines) is larger than the browser build's tables allow.

## Layout

| path                     | contents                                                     |
|--------------------------|--------------------------------------------------------------|
| `src/scc.h`              | shared tables, token and node kinds, capacities              |
| `src/util.sc`            | string interning, diagnostics                                |
| `src/lex.sc`, `src/pp.sc` | lexer (with exact decimal-to-double conversion) and preprocessor |
| `src/parse.sc`           | parser to an AST of indexed nodes                            |
| `src/types.sc`           | interned types and wasm32 layout                             |
| `src/sema.sc`, `src/expr.sc`, `src/call.sc`, `src/stmt.sc` | semantic analysis, following `compiler/src/Sema.cpp` |
| `src/memflow.sc`         | use after free and use after reset                           |
| `src/gen.sc`, `src/genx.sc`, `src/wasm.sc` | code generation and module assembly            |
| `src/vfs.sc`             | generated by `tools/genvfs.py`: the runtime and bundled headers |
| `src/driver_*.sc`        | entry points: native CLI, browser exports, stdin/stdout, debug dump |
| `runtime/rt.sc`          | the runtime compiled into every program                      |
| `include/`, `stdshim/`   | bundled C headers; playground implementations for std headers |
| `web/`                   | `scc.js`, `worker.js`, Node runners, API test                |

scc uses no pointers and no allocator. All state lives in fixed-size global
tables addressed by integer indices, with 0 meaning "none". That keeps it
inside the subset it compiles, and makes the same source build natively,
as wasm32 with `safec`, and with scc itself.
